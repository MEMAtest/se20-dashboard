# Journey Android companion

Small Java/framework Android application (Android 8 / API 26 or newer), with no runtime third-party dependencies. The main interface is the existing HTTPS Journey application in a restricted WebView. The home-screen widget is a real Android AppWidget using native RemoteViews, not a web shortcut.

## Use

1. Install the signed early-access APK from the latest GitHub release. Install over the previous version to retain widget settings; the signing identity is unchanged. It is not a Play Store listing. Review Android's prompts; do not disable Play Protect.
2. Long-press the home screen, choose **Widgets**, then **Journey** and your widget type. Widget setup lives in the launcher, not the Journey header.
3. Choose exact station search results, or a line for Line watch. Go home requires a home station; My journey requires both endpoints. Typed text alone is not a selected station.
4. Tap **Save widget**. Long-press to reconfigure. Next up opens Journey; its footer refreshes the source. My journey opens the selected endpoints, and its refresh checks times. Line watch opens the exact line; wider layouts also have refresh. Go home opens an explicit check screen: tap **Use phone location & update**, or update from a configured fixed station. It never requests location on its own.

| Widget | Starting size | Purpose |
| --- | --- | --- |
| Next up | 2 x 2 | Transport badge, destination, native min:sec countdown; following predictions use the same service and destination |
| Go home | 2 x 1 | Checked estimate to your home station, including wait before departure; optional display label such as SE20 |
| My journey | 4 x 2 | Leave countdown, absolute arrival and actual returned walking/transport legs, with overflow linked to the full route |
| Line watch | 2 x 1 | One chosen line's checked status; opens full details |
| Departures board | 4 x 4 | Optional original larger board, preserved for existing users |

Cell dimensions vary by launcher. Responsive native layouts adapt to available bounds, including a flat route view and smaller large-text variants. The white cards, cobalt timings, route pill, transport icons and tinted footers implement the second approved mockup; they are not image assets pretending to be working widgets. Chronometers use min:sec rather than the concept's rounded static minutes. Widget previews contain placeholders, not live predictions.

Widget settings are per widget, separate from browser favourites/Home. WebView storage is also separate from Chrome's PWA. No existing Home, favourites or listening data is overwritten. A Home destination is a selected station, not automatic address discovery. Phone mode requires an explicit foreground request and permission, rejects stale/imprecise fixes, stops location updates immediately after a fix or when leaving the activity, and stores no coordinates in the widget. Coordinates are sent to TfL for the requested route, not kept in widget storage. There is no background-location permission or location history service. A fixed station requires no GPS and can refresh through the ordinary job.

## Data and update boundaries

### Hosted web updates

Ordinary web screens, route planning and map changes do not require another APK. The installed 0.3.0 package loads the hosted HTTPS app. Web releases now use a content fingerprint generated by `node scripts/stage-assets.mjs`; deploy the generated staging files together, never the raw template files. The release marker, HTML, scripts and service worker must come from that same staging run.

When online, the web app checks on opening, returning to the foreground and reconnecting. A complete installed web release refreshes automatically when safe. It defers during active journey navigation or unfinished interaction, preserves temporary route fields across the refresh, and does not erase saved Home/favourites or replay old live predictions. Saved shows the loaded web version and update status. Offline or failed checks keep the available cached app with an explicit warning, not a claim that it is latest. The initial upgrade from an older web shell can refresh that shell once automatically.

Native widget layout/code, Android permissions and the wrapper itself still require an APK update. Web update acceptance is distinct from actual physical-phone acceptance; never infer the latter from a browser or unit-test result.

- Public TfL HTTPS reads only: search, verified station detail, at most four actual prediction boards individually, and at most eight line-status IDs. Entrances/access areas are not prediction boards; hub IDs are not treated as guessed journey endpoints.
- TfL predictions do not include every National Rail service. Use the main app for its separate National Rail source and wider journey choices. Empty predictions do not mean all services are healthy or that no train exists.
- Countdown and data-age chronometers tick in the Android host from monotonic elapsed time, not provider polling. Absolute times are London times. A countdown is still based on a dated prediction, not a new live check. Following bus times are explicitly labelled as at-check values and never mixed across destinations/routes. Bus-pair responses resolve only the selected individual stop; search exposes separate directions for selection.
- Invalid, failed, expired and departed estimates are cleared on render. One non-waking inexact alarm requests local invalidation at expiry/departure; it performs no network work. Android may defer that alarm, so timely clearing is not guaranteed in Doze, after force-stop or unavailable host execution. The ticking source-age label makes ageing explicit even between source refreshes. Refresh before travel. No exact-alarm permission or wake lock is added.
- Approximately 30-minute network-constrained background jobs while non-phone widgets exist, subject to Android battery/network quotas. Phone Home has no background location or network jobs. Manual source checks are rate-limited to one attempt per widget per 30 seconds. No exact alarms, foreground service, push subscription, paid backend or continuously running model.
- Partial-board failures and unavailable line alerts stay explicit. HTTP 429 / other source errors never create fabricated departures. Cached successes retain their original checked time after a failed refresh.
- Deleting a widget removes its settings and cancels its jobs. Reboot/package replacement restores jobs only for existing configured widgets.

## Build and tests

Use Java 17, Android SDK platform/build-tools 36, and the checked-in Gradle 8.14.3 wrapper (distribution SHA-256 pinned). AGP 8.13.0 is pinned. Do not install into another project's SDK or dependencies.

```sh
cd android
./gradlew --no-daemon :app:testDebugUnitTest :app:lintDebug :app:assembleDebug :app:assembleDebugAndroidTest
```

JVM tests cover source filtering, deduplication, London/DST clocks, earliest returned arrival, exact line identity, adverse statuses, endpoint encoding, entrance exclusion and honest no-data states. Node tests cover phone/line/station widget URLs, deferred exact-line opening, no automatic widget GPS lookup, Home preservation and invalid-link rejection.

`DeviceChecks` is a separate instrumentation test APK, not part of the release app. With a named, task-owned emulator, install the debug app and its test APK, then run `com.mema.journey.debug.test/com.mema.journey.DeviceChecks`. `-e live true` explicitly enables a bounded real TfL check; optional `-e station london-bridge -e render true` renders actual native RemoteViews into a test-only PNG. This is not a launcher-placement, button-tap, physical-phone GPS or unattended-scheduler acceptance test. Do not silently turn these checks into recurring runs.

`-e family true` runs 24 native fixture renders at minimum/standard/wide bounds and 1.0x/1.3x text, plus failure, exact-expiry, no-fabricated-legs and source-age checks. It checks vertical text bounds and horizontal countdown fit, and writes a labelled matrix/overview. With explicit `-e live true`, it additionally reads a real bus board, two real routes (including fixed-origin Home) and exact-line status, then renders them and checks their counters. This is not phone GPS, physical-launcher taps or guaranteed unattended alarm acceptance.

## Signing and distribution

From the repository root, set `JAVA_HOME`, `ANDROID_HOME` and an absolute canonical `JOURNEY_OUTPUT_DIR`, then run `node scripts/build-android-release.mjs`. It builds/tests and signs a release APK with a dedicated local Journey key. It never reuses another app's key. Preserve `~/.android/journey-signing/` securely: both the key and its password are needed for future compatible updates. They are outside the repository with restrictive permissions and must not be uploaded, printed, committed or included in website staging.

Only the signed APK and non-secret release manifest/checksums belong on the GitHub release. The Cloudflare website uses an explicit client-only staging allowlist; Android source, build outputs, tests, private keys and Gradle files are not served by the website.

## Security choices

No JavaScript-to-native bridge; only the exact Journey HTTPS origin is navigated inside WebView. Other HTTP(S) destinations open the system browser; non-web schemes are rejected. File/content access and mixed content are disabled; TLS errors are not bypassed. PendingIntents are explicit and immutable. Widget refresh receiver is not exported, configuration IDs must belong to this provider, and the job service requires Android's BIND_JOB_SERVICE permission. Backups/device transfer are excluded. Release builds are not debuggable. The app uses no analytics, advertising ID or payment account.
